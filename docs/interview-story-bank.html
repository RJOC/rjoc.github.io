1. ClickFix — PowerShell via Run Dialog

Endpoint

Customer environment · confirmed compromise · escalated

The tightened narrative

"I picked up an alert where PowerShell had spawned as a child of explorer.exe — significant because that pattern points to a Run-dialog execution rather than a normal script launch. Before digging further, I pulled the user's role from Entra ID and found they were in a non-technical, customer-facing role, so PowerShell activity on that account was already unusual on its own.

I checked the SIEM and saw the user had browsed to an atypical site shortly before the PowerShell execution — consistent with a ClickFix-style attack, where a fake CAPTCHA page tricks the user into pasting and running a command via the Run dialog. I confirmed that by pulling the RunMRU registry key, which showed the literal command typed into the Run box: a plaintext PowerShell one-liner using curl to pull down a second-stage script.

At that point I treated it as a confirmed compromise rather than investigating further while the host stayed live — our EDR had already logged the outbound connection, so isolating it wouldn't cost me that visibility, it would just stop anything further. I isolated the host through our standard containment playbook and disabled the user's account. I then checked whether any other users had hit the same domain to rule out a broader campaign — that came back clean, so I scoped it as an isolated incident.

I added the domain and related indicators to our blocklist, documented the full timeline, and escalated to the customer with two recommendations: implement an execution policy restricting PowerShell for standard users, since nothing was blocking it here, and add user awareness training on fake-CAPTCHA social engineering, since that was the actual entry point. The deeper reverse-engineering of the second-stage payload was handed to a specialized resource — determining exactly what it did wasn't something I tracked to closure myself."

Lock these down

  • Parent process is explorer.exe, not chrome.exe — chrome is just where the user hit the fake CAPTCHA page.
  • Evidence chain in order: Entra ID role check → SIEM browsing history → RunMRU registry (actual command) → confirmed compromise.
  • Why isolate immediately: EDR already logged the outbound connection, so isolating cost zero visibility — say this reasoning explicitly, it's the strongest line in the story.
  • Second-stage payload outcome is genuinely unknown / handed off — say that plainly, don't guess.
Still verify for real: who actually executed the host isolation — you, or was it done via a pre-approved automated playbook, or did it require the customer's retainer? This shifted three times in tonight's run-through. Check the ticket and get one clean answer before Thursday.

2. Phishing Email — User-Reported

Email

O365 / Exchange · solo-owned · true positive

The tightened narrative

"A user reported a phishing email through the O365 report button, which quarantined it and fired an alert — though our phishing analyzer's enrichment didn't populate this time, so I worked it manually. I called the user directly and walked them through pulling the raw email from Exchange so I could get the full headers.

Looking at the headers, SPF and DKIM both failed, and the Return-Path didn't match the visible From address — three converging signals, not just one. That was enough to act. I made the block decision based on the header analysis alone, without waiting to sandbox the URL first, because blocking a URL and sending domain org-wide is a cheap, reversible action — if I'm wrong, I just unblock it. The priority was making sure no one else in the environment could reach that link while it was still sitting in other inboxes.

I then scoped it — searched for any other users who'd received mail from the same domain, and found two more who had it in their inbox but hadn't interacted with it. I purged the message from their mailboxes, notified them, documented the full timeline, and closed it out as a true positive."

Lock these down

  • Three signals, not one: SPF fail + DKIM fail + Return-Path/From mismatch — don't just say "DMARC failed" on its own, that's not proof by itself.
  • Why you blocked before sandboxing: low-cost, reversible action, speed matters more than certainty here — contrast this explicitly with a higher-stakes action like host isolation if asked.
  • Be precise about "hadn't opened" vs "hadn't clicked" — know which one you actually verified.
Still verify for real: what system actually feeds the URL click-tracking data inside BlueMatter for this customer — Safe Links, a secure email gateway, something else? Confirm this with a teammate or the docs, don't guess it live in the interview.

3. Impossible Travel — GlobalProtect VPN

False Positive

Identity · newly onboarded VPN tech · tuned after close

The tightened narrative

"I picked up an impossible-travel alert and started with the basics — user, source IP, ASN. The first login was from the user's normal, AD-confirmed work location. The second was from an IP range I didn't recognize, so I checked it in VirusTotal — a community comment flagged it as Palo Alto Networks, and I cross-validated that independently through a WHOIS lookup rather than trusting the comment alone. It turned out to be a GlobalProtect VPN egress range the customer had just onboarded, before we'd tuned alerting for it.

I corroborated it further — MFA had succeeded on both logins, and the second one fell within the user's normal working hours, both pulled from AD enrichment. No containment was needed. The reason this isn't real impossible travel is the alert logic itself: it assumes source-IP geolocation reflects where the human physically is. A VPN egress node's geolocation reflects where the VPN server is hosted, which can be a completely different location from the user — so there was no actual travel to explain, the alert's underlying assumption was just broken by the VPN.

I documented it and tuned out the known GlobalProtect ranges for that customer, though the better long-term fix is tuning by ASN or vendor rather than a static IP list, since VPN providers rotate and add egress IPs constantly. Closed as false positive."

Lock these down

  • Have the impossible-travel mechanism memorized word for word — this gets asked as a standalone definitional question too, not just inside a story.
  • VirusTotal methodology: community comment as a lead, WHOIS as the validation — don't skip the second step when you tell it.
  • Corroboration beyond the IP: MFA success + working-hours pattern from AD — this is what actually closes the loop on "was this really the user."

4. EDR Auto-Quarantine — Discord Download

Endpoint

Malware · auto-contained by EDR · true positive

The tightened narrative

"EDR had already flagged and quarantined a malicious file on a host by the time I picked up the ticket. I logged in and confirmed the quarantine, then checked process creation events to see whether anything had actually executed and spawned before the quarantine caught it — that's the real question once something's quarantined, since the file being blocked doesn't guarantee nothing ran first.

In the SIEM, I traced it back to the user downloading the file directly from a Discord link. Rather than recommending a blanket block of the whole platform — which could create real friction if any team legitimately uses Discord — I recommended a more targeted fix: content-category filtering or application control on executable downloads regardless of source, which addresses the actual problem instead of just this one site.

I documented the full timeline, escalated to the customer, and closed it out as a true positive."

Lock these down

  • Keep the checks scenario-specific: process creation and persistence (run keys, scheduled tasks), not RunMRU or mailbox rules — those belong to different attack vectors, don't carry them over.
  • The recommendation should be precise, not blanket — "block Discord" is weaker than "filter by category / control executable downloads regardless of source."
  • Say it as true positive from the start — this is the one that got corrected mid-sentence tonight, make sure it's automatic by Thursday.
